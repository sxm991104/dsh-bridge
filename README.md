# dsh-bridge

**v1.1.0** · [更新日志](CHANGELOG.md) · [接下来往哪走](ROADMAP.md)

让 QQ 那边的 AI 能把活派给电脑上另一个自己，干完再回来说一声。

**这不是一个「聊天机器人框架」。** 它解决的是一个很具体的问题：

> 你在外面，用手机 QQ 让 AI 帮忙改点东西。但它只在 QQ 里，没有终端、没有文件系统，什么都动不了。

这个桥就是那条线：QQ 端把事写下来 → 电脑端接过来干 → 干完把结果送回去。

**从 v1.1.0 起，任务端不用装 DeepSeek Harness 了。** 自带引擎，任何 OpenAI 兼容的接口填进去就能跑——OpenAI、DeepSeek、通义、Kimi、本地 Ollama 都行。详见 [任务端](#任务端任何-openai-兼容的接口)。

## 为什么这么设计

### 一、派活必须「不等」

最早写的是同步等结果。**真干活要几分钟，而 QQ 那边等不了那么久。**

结果就是：电脑端明明 194 秒跑完了、成功了，QQ 端 2 分钟就断了，只能说一句"超时"。

**更糟的是分不清"还在跑"和"卡死了"** —— 两个都叫超时。

所以拆成两个动作：
- `dispatch` 写一条就返回，0.2 秒
- 后台进程慢慢跑，跑多久都行

### 二、要有一个「同一个窗口」

每次 `dsh qqme "任务"` 都是新进程。**新进程不知道上次干了什么，等于每次都是第一次见你。**

`headless` 支持 `--session-id <id>`，文档写的是 **adopt**（接手已存在的会话），不是新建。

实测：
```
进程 A：记住暗号「鲸鱼七号」
进程 B（完全新开）：问暗号 → 「鲸鱼七号」
```

**换进程，但窗口是同一个。** 会话号存在 `.session_id`，第一次跑的时候从事件流里抓出来。

### 三、心跳要说清「在做什么」

只报"还在跑"没用 —— 用户看不到它在干什么，跑错了也没法及时收住。

所以心跳（`.progress.json`）里带了 `doing`：从 `--json` 事件流的 `tool_call` 里取最后一个工具调用。

```
正在跑，已 20 秒（心跳 3 秒前）
在做：pwsh: Get-PSDrive C（check disk space）
```

### 四、任务要有「交差规则」

派过一次"查资料"的活，**跑了 28 分钟还没完。**

查事件流才发现：核心结论十分钟就拿到了，后面全在追新冒出来的相关论文（查"压缩摘要"追到 YaRN，从 YaRN 追到 Infini-attention），遇到 429 限流还一遍遍重试。

**每一步都合理，合起来无底洞。** 因为"调研"这类任务没有天然终点：写代码跑通了就是通了；查资料永远能再查一个。

所以派活时会自动附加三条规则（不改任务内容，只加判断标准）：
1. **能回答了就交** —— 手上的东西够了就停，别去找"更全面的资料"
2. **拿不到就记下来、停** —— 重试不超过两次，失败也要报
3. **别扩大范围** —— 查到别的东西记一句就够，别顺着往下查

## 装之前，先看这几条

**这玩意儿只在 Windows 上跑过。** 里面有一半代码是为了绕开 Windows 的坑。

**你需要：**
- [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（`dsh` 命令能跑）
- 一个能跑 `dsh headless` 的 profile（下面讲怎么配）
- Python 3.10+
- `pywin32`（只有 `watchdog.py` 需要——它用 Windows 的目录变更通知）

**你还需要知道：**
- 它默认给电脑端**全权限**（`danger-full-access`），跟桌面版同一个权限级别
- 所以「能看到它在干什么」和「能随时停掉」不是可选项，是必须的

## 配置

### 1. 准备一个 headless profile

在 `$DSH_HOME/profiles/` 下建一个目录（比如 `qqme`），放一个 `cordis.patch.yml`：

```yaml
# 用官方 API key 通道（按量付费，支持图片）
- id: agent-default-model
  name: "@deepseek-ai/dsh-agent-default-model"
  config:
    provider: deepseek-official
    model: deepseek-flash

# 人格（可选，但强烈建议写——不然它就是个没有性格的执行器）
- id: system-prompt
  config:
    personaPrefix: |
      你是……（写你想要的样子）
```

**为什么用 `deepseek-official` 而不是别的通道：**

- 有每日额度上限的通道，超了任务就哑了，而人在外面时没法充值
- 有些代理通道是纯文本的，会直接拒绝图片（见下面「踩过的坑」）

### 2. 设置环境变量

| 变量 | 作用 | 默认 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 官方 API key | 从 `$DSH_HOME/.credentials.yaml` 读 |
| `DSH_HOME` | DSH 数据目录 | `~/.dsh` |
| `DSH_CMD` | dsh 可执行文件路径 | 从 PATH 找 |
| `DSH_PROFILE_FILE` | qqme 的 patch 文件 | `$DSH_HOME/profiles/qqme/cordis.patch.yml` |

`bridge.py` 会自己从 `$DSH_HOME/.credentials.yaml` 里捞 `DEEPSEEK_API_KEY`，**不用把 key 写进代码。**

## 任务端：任何 OpenAI 兼容的接口

**这是 v1.1.0 最大的变化。** 以前任务端必须跑在 DeepSeek Harness 里，用户想用得先装 DSH——这对很多人是劝退的。

现在自带一个引擎，只要三样东西：

```
接口地址   base_url
API Key   api_key
模型名     model
```

**填在哪：** 桌面端「设置 → 任务端用哪个模型」，填完点「测试连接」，通了再保存。

**模型名不用自己查。** 填好地址和 Key，点「测试连接」，它会去问这个接口**你有哪些模型**，拉回来做成下拉框。

为什么要这样：**服务商的模型名是会变的。** Kimi 把 `moonshot-v1-8k` 下线了，官方文档里还写着它；照文档填就是 `404 Not found the model`，报错还是英文的，用户根本不知道该填什么。**下拉框里的名字是服务商自己给的，不会错。**

**常用的几个：**

| 服务 | 接口地址 | 模型名（示例，以你账号下拉框里的为准） |
|---|---|---|
| OpenAI | `https://api.openai.com` | `gpt-4o` |
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode` | `qwen-plus` |
| Kimi | `https://api.moonshot.cn` | `kimi-k2.6` |
| 硅基流动 | `https://api.siliconflow.cn/v1` | `deepseek-ai/DeepSeek-V3` |
| 本地 Ollama | `http://localhost:11434` | 你本地有的那个 |

配置存在 `%APPDATA%\dsh-bridge\engine.json`，key 不进代码、不进仓库。

### 可以同时开好几套，各跑各的

**不是「切换」，是「同时都在干活」。**

```
Kimi       最多同时跑 2 个
DeepSeek   最多同时跑 1 个
通义       最多同时跑 1 个
```

每套配置有自己的并发上限，满了排进**这套自己的**队列，等有空位由后台线程自动拉起来——用户派完就关窗口了，不该回来盯队列。

**并发该填多少，取决于你手上的 Key：**

- 免费额度卡得紧的（比如 Kimi 免费版每分钟 3 次请求），填 1~2，多个并行反而互相抢、一起变慢
- 按量付费、没限制的，可以填 3~5
- 填大了不会报错，只是大家一起排队等限流

**这个数字是调速，不是限制。** 窗口想开多少开多少，那是磁盘上的目录。

### 派活时可以指定用哪套

前台（QQ/飞书那边）加了两个工具：

```
list_computer_models    看看现在能用哪些模型
send_to_computer(task, task_name, model="kimi")
```

用户说「派给 Kimi」，前台就能把活送到 Kimi 那套上。名字不用完全对，模糊匹配就行。

### 引擎里有什么

```
engine/llm.py        发请求、解析工具调用、认得出 401/429/500 分别是什么意思
engine/tools.py      六个工具：读文件、写文件、改文件、列目录、搜内容、跑命令
engine/session.py    会话存盘，上下文长了自动压缩
engine/agent.py      工具循环——让模型自己决定调什么、调几次
engine/profiles.py   多套模型配置，各跑各的
engine/scheduler.py  并发上限 + 排队，满了自动轮到下一个
engine/ratelimit.py  按服务商的频率限制排队（每分钟几次那种）
engine/models.py     问接口"你有哪些模型"，给界面做下拉框
```

**只有六个工具，是故意的。** DSH 有几十个，但任务端真正用到的是这几个，工具越多模型越容易挑错。

`edit_file` 单独列出来是因为：让模型「整篇重写」来改一个字符，既慢又容易改坏别的地方。精确替换能让它只动该动的那一行。

### 会话

**一个任务 = 一个工作目录 = 一份记忆。**

```
workspaces/<任务名>/.session.json     ← 完整的对话记录
workspaces/<任务名>/                  ← 它的工作目录
```

**这意味着「继续」是真的继续**，模型记得之前做过什么，不用重新摸一遍。删掉任务目录，记忆跟着没，不会有孤儿数据。

**相对路径以任务目录为准。** 模型说 `write_file("test.txt")`，文件就落在那个任务的目录里，不会跑到别处。

### 上下文长了会自己压缩

超过大约 6 万 token 时，把最早那批消息压成一段摘要——保留用户说过的需求、助手给过的结论，砍掉中间的来回对答。

**不调模型去摘要**，因为那要多花一轮 token、多等一次响应，而且摘要本身也可能丢关键信息。这里做的是保守的"捞要点"，够用且不引入新的不确定性。

### 和 DSH 的关系

**配好了就用新引擎，没配就退回 DSH。**

保留退回这条路是为了不让老用户卡住——他还没填配置时，至少原来能跑的东西还能跑。填好之后 DSH 就完全用不上了。

## 用起来

```bash
# 派一条任务，立刻返回
python bridge.py dispatch "在 D:\Project\demo 下建个 README.md，写三行简介"

# 真干活（一般在后台调）
python bridge.py run --id t-20261027120000

# 看进展
python bridge.py live
# → {"running_tasks": [...], "progress": {"doing": "write_file: README.md", ...}}

# 看某个任务
python bridge.py status --id t-20261027120000

# 停掉卡住的
python bridge.py cancel --id t-20261027120000

# 看它卡在哪儿（拿不到东西时会写这里）
python bridge.py ask

# 切模型/通道（模型和通道绑在一起，用"预设"一次切对）
python tune_model.py show
python tune_model.py options
python tune_model.py set --preset cb-flash         # codebuddy 4.1-flash（省钱，有每日额度，看不了图）
python tune_model.py set --preset cb-pro           # codebuddy 4-pro（省钱且更强）
python tune_model.py set --preset official-flash   # 官方 API（按量付费，无额度，能看图）
python tune_model.py set --effort high             # 只调推理强度（仅 codebuddy 认，无 medium）

# 给项目加 git 防护（别让 AI 的草稿进仓库）
python guard_git.py list
python guard_git.py apply D:\Project\某个项目
```

**任务状态：**

| 状态 | 含义 |
|---|---|
| `pending` | 排队中 |
| `running` | 正在跑（心跳里有 `doing`） |
| `ok` | 做完了，有结果 |
| `empty` | 跑完了但没输出 |
| `error` | 出错 |
| `timeout` | 超时，进程已连根杀掉 |
| `cancelled` | 手动停的 |

## 桌面端

一个 Windows 程序，双击打开。不用装 Python，不用开命令行。

```
任务     派活、看进度、看结果
服务     QQ 和对话服务的启停，状态一眼看到
设置     模型配置、程序路径、开机自启
```

**它只认桥的 HTTP 接口，不认 AstrBot。** 以后前台换了框架，这个界面一行不用改——桥是那个稳定的中间层。

### 启动服务：全程零黑窗口

这块比看起来麻烦，踩了几个坑才做对：

| 问题 | 怎么解决的 |
|---|---|
| QQ.exe 是控制台程序，自己会建黑框 | 启动后盯住，见一个藏一个 |
| 对话服务从 exe 启动会再拉两层 Python | 用 `pythonw.exe` 直接跑，压根不创建控制台 |
| 重复点击会起多个实例 | 先查进程和端口，已在跑就直接复用 |

### 扫码登录

QQ 登录态失效时需要扫码。NapCat 会把二维码写到 `cache/qrcode.png`，桌面端读出来直接显示在界面上，带倒计时（剩 30 秒变警告色）。

**过期了会自动重启 QQ 换一张新的**，不用用户自己去找。

点「不管了，停掉」就是真的停掉 QQ，回到干净状态——不是把窗口关掉了事。

### 路径不写死

QQ、NapCat、AstrBot 装在哪儿，第一次打开会自动探测（查注册表 + 常见位置），探测不到让用户点「选择…」自己指，选过就记在 `%APPDATA%\dsh-bridge\config.json`。

**探测结果只填进输入框，要点保存才作数**——万一探测错了，不会把好用的配置覆盖掉。

### 它只做一个程序

接口服务和界面在同一个进程里。任务管理器里出现三个 `python.exe` 会让普通人以为是病毒。

## 踩过的坑（这部分可能比代码有用）

### 编码：`stream.read()` 会阻塞到进程结束

第一版读子进程输出用的是 `stream.read()`。**它是阻塞的，要等进程退出才返回。**

结果：心跳每 5 秒去读输出缓冲区，永远是空列表 —— `doing` 字段一直是空的，用户看不到它在做什么。

**改成 `readline()` 循环**，来一行存一行。

### 编码：Windows 子进程输出是 GBK

症状：文件里中文全对，但 QQ 那边收到一堆 `�`。

原因链：
1. 子进程 stdout 编码由 `PYTHONIOENCODING` 决定，没设时跟随系统 ANSI 代码页（中文 Windows 是 cp936/GBK）
2. 我们按 UTF-8 去解 → 全碎

**试过但没用的两种修法：**
- `subprocess.run(..., encoding="utf-8")` —— 没用，字节已经在子进程那边按 GBK 生成了
- 给子进程传 `PYTHONIOENCODING=utf-8` —— 对 `dsh.cmd` 这种批处理没用，它拉 node 时不一定带下去

**最后有效的做法：拿 bytes，先试 UTF-8 严格解码，失败再用 GBK。** 不依赖任何外部设置。

### 权限：`SetNamedSecurityInfoW failed (Win32 5)`

`dsh` 的沙箱默认是 `workspace-write` —— 只能写**一个**工作目录。

换工作目录治不了，因为沙箱只认"一个可写根"。症状是让它在另一个盘建文件，报 `Access denied [sandbox: file access denied under workspace-write]`。

**根子在这里**（`dsh --dump-config` 能看到）：

```yaml
- id: sandbox-policy
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
```

**塞一个环境变量就够：** `DSH_PERMISSION_MODE=danger-full-access`

**但有个坑：权限是在「会话创建时」固定的。**

带 `--session-id` 接手旧会话时，权限还是旧的，改环境变量没用。**必须删掉旧会话号重建一次。**

### 事件格式：别猜字段名，去看真的

`tool_call` 事件的真实结构是：

```json
{"type": "tool_call", "tool": "pwsh", "input": {"command": "Get-Date", "description": "..."}}
```

我一开始猜的是 `name` / `args`，写错了也不知道 —— 因为解析失败不报错，只是返回空字符串。

**如果没有实测抓一遍原始事件，这个 bug 会一直藏着。**

### `turn_end` 里的错误不是顶层 error

`dsh` 把「这一轮失败了」包在 `status` / `turn_end` 里：

```json
{"type":"status","phase":"turn_end","reason":{"kind":"error","error":{...}}}
```

只认顶层 `type=error` 的话，这类失败会被当成"跑完了没说话"，**状态还记成 ok**。

实测代价：把推理强度设成模型不支持的档位，任务真失败，但显示成功、耗时 12.6 秒、结果空字符串。

**假成功比失败更害人 —— 用户以为活干完了。**

### 推理强度：不是所有模型都认所有档位

`medium` 这个档 `deepseek-v4.1-flash` 不支持，设了会报 `UNSUPPORTED_REASONING_EFFORT`，整个任务白跑。

**能用的：`low` / `high` / `max`。**

### 沙箱的 ACL 改不了时，换个目录

`D:\` 下的目录，沙箱要改安全描述符（加专用 SID + 加 deny + 把完整性标签降为 Low），那一步会失败。

**`C:\Users\<你>\Downloads` 下面是能接管的**（那里本来就有沙箱标记：deny FILE_DELETE_CHILD、专用 SID、Low 完整性标签）。

**如果 `danger-full-access` 也起不来，先把工作目录换到 Downloads 下面试试。**

### 超时杀不干净，会话就永久锁死（最难查的一个）

这个坑值得单独写，因为**从外面完全看不到**，而且症状会把人引到错误的方向上。

**症状：** 同一个任务重跑，报

```
session "session-xxx" is already owned by an active write handle
```

**第一反应是去找锁文件。** 翻遍 `.dsh/sessions/<会话>/` 只有 `session.v4.jsonl.zstd`，**没有锁文件。**

**第二反应是以为和别的任务抢会话。** 也不是——那个任务早就结束了。

**真相：** `taskkill /F /T` 杀掉了进程树，但 dsh 拉起的不只是 `node.exe`，**还有它自己再拉的 `DeepSeek Harness.exe` 子进程**。任务被强杀时，这些孙进程偶尔会脱离父进程树，`/T` 就够不着了。

它们活着、握着会话的写句柄，而**任务状态早就写成 error 了**——所以看哪儿都像"任务已经结束"。

**怎么认出来：** 这些僵尸内存只有 **4 MB 左右**，CPU 时间几乎不涨。跑了几十分钟，任务管理器里一眼扫过去根本注意不到。

实测抓到过 4 个：跑了 17~38 分钟，全是 4 MB。

**怎么修：** 杀之前先抓快照。

```python
# 错的：直接杀树，脱离父树的孙进程收不到
subprocess.run(["taskkill", "/F", "/T", "/PID", str(proc.pid)])

# 对的：先记下所有子孙，杀完树之后按 PID 补刀
children = _child_pids_snapshot(proc.pid)   # wmic 查 ParentProcessId 关系
subprocess.run(["taskkill", "/F", "/T", "/PID", str(proc.pid)])
for pid in children:
    subprocess.run(["taskkill", "/F", "/PID", str(pid)])
```

**关键是"按 PID 补刀"，不是"按名字扫"。** 按名字扫（比如杀掉所有 `DeepSeek Harness.exe`）会误伤桌面端自己那个主进程——那是另一个程序，杀掉等于把用户正在用的东西关了。

**为什么这个 bug 值得记住：**

- 查文件查不到 → 你会一直往"文件锁"的方向查
- 任务状态是 error → 你会以为任务已经结束了
- 进程只有 4 MB → 任务管理器里看不见
- 三个假象叠起来，能让人查半天

**而且它会自己恶化：** 每跑几十个任务积一批僵尸，攒够了整个调度就瘫了。上线后才撞上的话，基本查不出来。

### Windows 的 os.replace 会失败，POSIX 不会

多个任务同时更新 `tasks.jsonl` 时：

```
PermissionError: [WinError 5] 拒绝访问
  os.replace('tasks.jsonl.tmp.22112', 'tasks.jsonl')
```

**POSIX 允许原子替换一个正被打开的文件，Windows 直接拒绝。**

三个任务时撞不上，十个一压就有一半进程崩在启动阶段——状态卡在 pending，其实进程早退了。

**修法不是加锁**（试过，没用——锁只保护自己那段代码，挡不住别人已经打开的文件句柄），**是失败重试。**

### 后台线程碰界面，只有一条路：Signal

写桌面端时撞了两次同一个墙。

```
❌ QTimer.singleShot(0, lambda: self._show(data))   从后台线程调
✅ self.got_data.emit(data)                          信号
```

**从一个非主线程调 `QTimer`，那个计时器不会进主线程的事件循环，回调永远不执行。**

问题是它**不报错、不崩溃，只是静默失效**。表现是：二维码一直显示"正在取二维码…"，而后台其实每次都拿到了数据。

第一次在扫码头那里撞上，修好之后写 `request_once` 又踩了一遍——设置页的路径输入框永远空着。

**记住：跨线程改界面，用 Signal。没有第二种办法。**

### 界面闪烁，不是"多画了一次"

用户说"桌面端自己在乱闪，点哪儿都没反应"。查了半天颜色、样式、定时器，都不是。

**真正的原因是一次刷新 435 毫秒。**

```
任务列表每 3 秒刷一次
每次把 102 个 TaskRow 全销毁再全新建一遍
→ 界面有 15% 的时间在重建控件
→ 加上布局连锁反应，看起来就是持续闪烁
→ 主线程被占着，点什么都没反应
```

**修法：结构没变就原地更新文字，不重建。**

```
之前 435 毫秒 → 现在 17 毫秒
```

**顺带挖出两个同类问题：**

- 转圈控件的定时器写在构造函数里，卡片一创建就挂一个 60ms 的，谁也停不了。改成跟着可见性开关。
- `QScrollArea` 的 `setWidgetResizable(True)` + 内容里有 `addStretch()` = 布局死循环。Qt 要算"内容高度取决于可用空间 → 可用空间取决于滚动条 → 滚动条取决于内容高度"，永远算不完。

**这三个的共同点：都是在定时回调里无条件重做昂贵的事。**

### 但那次闪烁其实不是代码的问题

上面这些确实该修，**但用户当时看到的那个闪，是耳机压在笔记本触摸板上。**

触摸板被持续按住，系统一直在发鼠标事件，界面就一直重绘。代码没问题。

**这条写在这儿是因为它比前面三条更值钱：**

排查性能问题，第一件事是**先确认现象真的是软件造成的**。

当时的做法是错的——用户一说"闪"，我直接开始读代码、装计数器、量重绘次数。量出来的数字都是真实的（435 毫秒、3266 次 PaletteChange），**但它们解释不了那个闪**，于是我在这条错误的线索上越挖越深。

**正确的第一句应该是：「你手上、桌上、触摸板上有没有压着东西？」**

一个三十秒的问题，能省掉一下午。

### 路径少算一级，整个功能静默失效

`engine/scheduler.py` 要读 `tasks.jsonl`，它自己住在 `engine/` 子目录里：

```python
BRIDGE_DIR = os.path.dirname(os.path.abspath(__file__))   # ← 这是 engine/，不是桥目录
```

于是它一直在读 `engine/tasks.jsonl`——**那个文件不存在。读不存在的文件返回空列表，而空列表让所有并发检查都通过。**

```
配置写的是"最多同时跑 2 个"
派 6 个任务
→ 6 个全跑起来了
→ 没有任何报错
```

**这个 bug 的可怕之处就是它不报错。** 文件读不到是"正常"的、列表是空的是"正常"的、检查通过也是"正常"的。**功能整个失效，日志一片安宁。**

正确的写法：

```python
BRIDGE_DIR = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
```

**教训：凡是"读文件 → 根据内容做判断"的代码，先把路径打出来看一眼。** 读不到和读到空，在很多逻辑里是一回事，但它们的含义差了十万八千里。

### 先占位再检查，等于自己占了位子

修好路径之后，`conc = 1` 的配置**连第一个任务都排队，再也不跑**。

因为顺序反了：

```python
rec = cmd_dispatch(...)      # 写进文件，状态 pending
if has_slot(pid, limit):     # 这时它自己已经在文件里了
```

而 `pending` 是要算占位的（否则并发控制形同虚设）。**所以是"我自己刚占了一个位子，然后问还有没有空位"。**

```python
has_room = has_slot(pid, limit)   # 先问
rec = cmd_dispatch(...)           # 再落盘
if has_room: spawn()
```

**任何"检查 → 占用"的逻辑，顺序必须是先检查后占用。** 听起来是废话，但代码里一旦把"创建记录"和"占用资源"混在同一步，就很容易写成反过来。

### 失败却显示成功：`return` 早了一行

401 的任务，状态 `ok`，结果栏里躺着一句错误信息。

```python
except LLMError as e:
    messages.append({..., "content": f"（模型调用失败：{e}）"})
    prog.doing = f"失败：{e}"
    _save(workdir, messages, prog)
    return prog          # ← 这时候 prog.messages 还是空的
```

`prog.messages = messages` 写在函数末尾的正常路径上，**错误路径直接 return 跳过了它**。

上层 `final_text()` 从 `prog.messages` 里找最后一条 assistant 消息——找不到，只能退回 `prog.doing`，而那是"失败：接口返回 401…"，不以判定用的前缀开头，**于是被判成成功**。

修了两处：

1. 错误路径补上 `prog.messages = messages`
2. 判定从"看一个前缀"改成"三条里任意一条成立"——文案一旦被包一层就漏判，不能只认字面

**假成功比失败害人。** 用户看到 `ok`，以为活干完了，不会去查。

### 少一行 `addWidget`，控件被垃圾回收后一碰就崩

给设置页加配置列表，重写了一整块，漏了：

```python
lay.addWidget(card)      # ← 这行没了
```

后果：

```
card 建出来了
控件也塞进去了（cl.addWidget(...)）
但没有任何人引用 card
→ Qt 的垃圾回收把整棵子树销毁
→ self.ed_base 指向一个死掉的 C++ 对象
→ RuntimeError: libshiboken: Internal C++ object (QLineEdit) already deleted
```

**排查过程值得记下来，因为我先错了两次：**

| 猜想 | 怎么否掉的 |
|---|---|
| 重复创建，后一个覆盖前一个 | 搜赋值语句，只有一处 |
| layout 嵌套导致控件被 reparent | 读了完整结构，是对的 |

最后给 `QLineEdit.__init__` 打桩数了个数——**一共造了 7 个，死了 2 个**，死的正好是 `card` 里那两个。这才想到去确认它到底有没有被加进父容器。

**教训：`RuntimeError: Internal C++ object already deleted` 只有一个含义——这个对象的所有权链断了。** 别去猜哪行代码删了它，直接查它是不是根本没挂到父控件上。

### 回调存在共享变量里，并发时互相覆盖

```python
self._pending_cb = callback
self._once.emit(data)
```

两个请求同时发出，**后一个把前一个的回调覆盖掉**。前一个的数据回来时，调的是别人的回调。

表现：**「这次打开设置页什么都没有，下次又有了」。**

改成把回调跟着数据一起发出去：

```python
self._once.emit((data, callback))
```

**间歇性的 bug 最难查，因为单发一个请求永远测不出来。** 这类问题的共同点是"有个共享槽位"，一搜就能搜到——`self._pending_xxx`、`self._current_xxx` 这种命名，看到就该警觉。

### 服务商说「等 1 秒」，等 1 秒没用

`kimi-k2.6` 的免费额度是**每分钟 3 次请求**。跑一个任务要好几轮，必然撞上：

```
429 {"error":{"message":"... request reached organization max RPM: 3,
                please try again after 1 seconds"}}
```

第一版照着那个 `after 1 seconds` 等 1 秒——**没用**。因为限制是"每分钟 3 次"，等 1 秒还在同一个窗口里，必然再撞。

```
照它说的等 → 5 次重试全废 → 任务失败
```

改成从错误信息里读出**真实配额**，自己算：

```python
rpm = 3
间隔 = 60 / rpm * 1.2     # 24 秒，多留 20% 余量
```

**服务商告诉你的"等几秒"通常是统一话术，不是真实配额。真实配额得自己从错误信息里挖。**

### 推送发了，用户什么都没收到

日志写着「推了 1 条完成通知」，用户那边一片空白。

推送是把一条事件塞进队列，走**跟正常回复一样的链路**。而 `reply_with_quote` 是全局开关，于是推送也被包了一层引用：

```
MessageChain(chain=[Reply(...), Plain(...)])
```

- QQ 支持引用 → 没事
- **飞书不支持 → 整条消息发送失败**，adapters 报 `Failed to send the message chain`

**同一个开关，在 A 平台无害、在 B 平台致命。**

修了两处：

1. 推送对不支持引用的平台（飞书/Telegram/Slack/Discord）直接发，不走 pipeline
2. 引用守卫插件同时接管飞书的 `send`，把 `Reply` 一律摘掉

**还有第二层问题：** 原来只记"最后说话的那个会话"。在 QQ 说了话，目标就切到 QQ；那之后 QQ 一掉线，**推送彻底发不出去——明明飞书还通着**。

改成每个平台各记一份，发的时候挨个试，哪个活着走哪个。

### 留着一个过时的工具，比没有更糟

问「现在能用哪些模型」，模型调了 `tune_computer_model`——那是 DSH 时代的工具，管的是 codebuddy 三条通道，返回：

```
任务端现在走 codebuddy，模型 deepseek-v4.1-flash
```

**全是早就不存在的信息。** 新加的 `list_computer_models` 没被选中，因为两个工具名字都在讲"模型"，模型分不清哪个是对的。

**直接删掉旧工具。**

工具不是越多越好。**两个功能重叠的工具同时存在，模型选错的概率不是 50%，而是往更"像"的那个偏。** 而它看起来还很合理——所以用户会被误导，还以为是系统出了问题。

### 飞书返回 21001，查配置永远查不出来

飞书 API 全部返回：

```
{"code":21001,"msg":"Access denied due to platform policy."}
```

配置检查了一遍又一遍：App ID 对的、Secret 对的、权限全开了、版本已发布、可用范围没改。**一切正常，就是不通。**

搜下来不关我们的事：

- `2026-10-13` 起陆续有人报同样的错
- 飞书客服统一回复"技术排查中"，有人等了好几天
- 最后有人靠**重新创建一个企业账号**解决
- 标题点名了「豆包账号对自建应用的调用权限被收回」

**抖音/豆包渠道注册的飞书租户被单独限制了。** 换一个纯 `feishu.cn` 注册的企业账号，立刻恢复。

**这类问题的教训：查配置查不出来的时候，先去确认现象是不是别人的问题。** 我们的第一反应永远是"我哪里写错了"，但有些时候答案是"它那边不让你用了"。

## 服务挂了怎么办（watchdog.py）

**这是这个项目里最容易被忽略、但最要命的一块。**

### 问题

桥跑在 AstrBot 进程里。**AstrBot 一挂，桥跟着挂，然后没人能把它拉起来。**

如果重启这件事交给桥自己干：

```
桥让 AstrBot 重启
  → AstrBot 死
  → 桥跟着死（它在同一棵进程树里）
  → 没人再把它拉起来
```

死锁。**而这个死锁恰好在最要紧的时候发生：你人在外面，改完东西需要重启验证，结果一重启整个系统就没了。**

### 做法

一个**不在 AstrBot 进程树下面**的独立进程。它同时干两件事，这两条是**独立的线**：

**线一：被动听请求**

```
<桥目录>\restart.request      ← 谁要重启，往这里写一行
<桥目录>\restart.result       ← 守护把结果写回来
```

用 Windows 的目录变更通知（`ReadDirectoryChangesW`）监听，**内核推事件，没事件时零开销**。

**线二：主动体检**

**这一条才是"守护"的真正含义。**

第一版只做了线一。当时以为够了，直到有人点破：

> AstrBot 自己崩了、没人写 `restart.request`，它就干看着。

**对。没人请求的时候服务崩了，那才是最需要它的时候。**

所以加了体检：每 30 秒连一次端口，**连续 3 次不通（约 90 秒）才动手**。

为什么要连续 3 次——偶尔一次连不上（正在启动、系统卡顿）不算死。

**为什么体检只能轮询：** 服务死掉这件事不会通知任何人，没有可监听的事件源，只能去问。30 秒一次 TCP 连接尝试，开销可以忽略。

实测（暴力杀掉 AstrBot，不写任何请求文件）：

```
[15:15:18] 杀掉 AstrBot
[15:15:41] 体检：端口不通（第 1/3 次）
[15:16:13] 体检：端口不通（第 2/3 次）
[15:16:45] 体检：端口不通（第 3/3 次）
[15:16:45] 连续探测不到，判定服务已挂，开始拉起
[15:17:14] 自动拉起成功，用时 29.6 秒
```

**全程没人请求。**

### 拉起的时候，两条路

```python
# 路线一：start_astrbot.bat（正常走这条——它可能有环境变量设置）
# 路线二：直接 astrbot.exe run（bat 不可用时的兜底）
```

**为什么要有第二条：** 全指着那个 bat 的话，bat 一改坏、一删，守护就废了——而且是在最需要它的时候。

### 关于"要不要轮询"

合理的组合是：**听请求用事件，查死活用低频轮询。**

- 听请求：可以事件驱动，零开销，就用事件
- 查死活：没有事件源，只能轮询——但 30 秒一次可以忽略

**不是全都轮询，也不是全都事件。** 一开始我两样都想要事件，结果听请求那半确实该用事件，查死活那半根本没法事件。

### 三层防护（这些不是可选项）

| 防护 | 为什么必须有 |
|---|---|
| **冷却 5 分钟** | 我自己因为反复重启 AstrBot 被 QQ 踢下线过一次。重启太频繁会触发风控，这条就是挡这个的 |
| **连续失败 3 次就停手** | 免得变成"起了就崩、崩了再起"的死循环，把机器拖死。停手后写 `.stuck` 文件，等人来看 |
| **不碰 NapCat** | NapCat 自己会重连。重启它反而容易触发风控，得不偿失 |

### 用起来

```bash
# 装依赖（pywin32 用于目录监控）
pip install pywin32

# 指定 AstrBot 的启动脚本（或者把 start_astrbot.bat 放到同目录）
set DSH_WATCHDOG_START_BAT=D:\你的AstrBot目录\.bot_runtime\start_astrbot.bat
set DSH_WATCHDOG_PORT=6185

# 启动（pythonw 无窗口）
pythonw watchdog.py
```

**让它开机自启**（Windows）：

```powershell
schtasks /create /tn "dsh-watchdog" /tr "pythonw.exe C:\path\to\watchdog.py" /sc onlogon /rl highest
```

### 一次改写的记录

第一版监听是用 `ctypes` 直接调 `ReadDirectoryChangesW` 写的。

**实测：往目录里写文件，守护进程 CPU 一直是 0，没有任何反应。** 调用卡在里面不返回，参数拼错也不报错。

ctypes 拼 Win32 结构太容易出无声的错，**换成 `pywin32` 的 `win32file` 才正常。**

## 多开：能开到多少，取决于你自己的机器

这个桥支持一任务一会话、一任务一目录、多个任务同时跑。**但上限不是代码决定的，是你机器决定的。**

实测（16 GB 内存 / 16 核，任务内容是"只回一句话"最轻的那种）：

| 并发 | 结果 | 内存峰值 |
|---|---|---|
| 10 | ✅ 10/10 | 正常 |
| 20 | ✅ 20/20，78 秒 | 60% |
| 30 | ✅ 30/30，110 秒 | 75% |
| 50 | ✅ 50/50，201 秒 | 吃紧 |
| 100 | ❌ 内存爬到 91%，只剩 1.4 GB，手动叫停 | — |

**真实任务（改文件、跑命令、读大文件）单个吃得多得多，安全值要往下调。**

实际用起来一次三五件事，连"偶尔高峰"都碰不到。

### 压测挖出来的两个坑

**一、Windows 上 `os.replace` 会失败，POSIX 不会**

多个任务同时更新 `tasks.jsonl` 时：

```
PermissionError: [WinError 5] 拒绝访问
  os.replace('tasks.jsonl.tmp.22112', 'tasks.jsonl')
```

**POSIX 允许原子替换一个正被打开的文件，Windows 直接拒绝。** 十来个任务同时跑就有一半进程崩在启动阶段——状态卡在 pending，其实进程早退了。

这不是理论担心：**三个任务时撞不上，十个一压就现原形。** 而且它在真实使用中会随着任务数增长而变频繁，等你发现时已经很难查了。

**修法不是加锁，是失败重试**（试过加锁，没用——锁只保护自己那段代码，挡不住别人已经打开的文件句柄）。

**二、采样间隔会骗你**

第一版压测脚本每 3 秒采一次内存，报告"50 个并发峰值 61%，很安全"。

手动 2 秒一采才发现：**100 个任务的内存是在 40 秒内从 5.7 GB 爬到 1.4 GB 的**，脚本采样的那一刻恰好都在低点。

**监控粒度比监控本身更重要。** 如果你的采样间隔比问题的发生周期还长，你会得到一个让人放心的假结论。

## 已知限制

- **只在 Windows 上验证过。** Linux/macOS 应该能跑，但沙箱那部分行为不一样。
- **并发上限取决于机器，不由代码限制。** 内存不够时任务会失败，桥会识别并报"内存不足"，但不会替你排队。
- **`ask.jsonl` 不一定写得出来。** 规则里要求它卡住时写一行，实测模型经常不写，而是把失败直接写在答案里。通道留着，但不强求。
- **只用 DSH 时才依赖它的内部机制**（`DSH_PERMISSION_MODE`、`--session-id`、`--json` 事件格式）。换到自带引擎就没这个问题——两者是并行的两条路。
- **自带引擎验证过 DeepSeek 和 Kimi。** 其他兼容接口应该能用，但工具调用和参数格式各家有出入。已知 Kimi 只接受 `temperature=1`，引擎会自动去掉这个参数重发；限流按 `RPM` 自己排队。撞上别家就修。
- **并发上限是"调速"，不是"限制"。** 每套配置各填一个数字，满了排队由后台线程自动轮转。填大了不会报错，但同一个 Key 上并行太多会互相抢限流。
- **`kimi-k2.6` 免费额度只有每分钟 3 次请求。** 一个任务要好几轮，用它跑长任务会很慢。要快就用 DeepSeek 或者付费额度。
- **QQ 那一段还依赖 NapCat 和 AstrBot。** 见 [ROADMAP.md](ROADMAP.md)，这两处迟早要换。
- **反复重启 QQ 会被风控。** 实测过：一天重启十几次，账号进"禁言"状态（`Ban state forbit write req`），发不出任何消息。重启要珍惜。
- **抖音/豆包渠道注册的飞书账号会被限制。** `21001 Access denied due to platform policy`，配置全对也不通。换纯 `feishu.cn` 注册的企业账号。
- **没有鉴权。** 这是本机工具，别暴露到公网。
