# 交给 AI 的示例任务模板

派活的时候，任务写得越具体，它做得越准。
但**不需要把每个步骤都写死** —— 该让它自己判断的地方留白，反而更好。

下面几类是最常见的。

---

## 一、纯执行类（目标明确，结果可验证）

```
在 D:\Project\demo 下建一个 README.md，写三行项目简介：
第一行标题，第二行一句话说明，第三行技术要求。
写完把文件内容读回来贴给我，确认没有乱码。
```

**为什么这样写：**
- 动哪个文件、写什么，说死了
- **怎么确认成功，也说死了**（读回来验证）—— 不给它留"我觉得写好了"的空间

---

## 二、排查类（目标明确，路径未知）

```
D:\Project\某项目 跑 npm run build 报错了。
1. 先跑一遍，把完整报错贴出来
2. 定位到具体是哪个文件哪一行
3. 说清楚原因
4. **先别改**，把改法告诉我就行
```

**为什么加"先别改"：**
排查和修改是两件事。混在一起容易改错地方，而且你还没看见原因它就已经动手了。

---

## 三、调研类（最容易跑飞的）

```
只读这三个页面：
  - https://xxx/1
  - https://xxx/2
  - https://xxx/3
把每个页面里「局限性」那一段摘出来，合并成 500 字以内。
到此为止，不要点开任何其他链接。
```

**为什么这么写：**

调研天生没有终点 —— "查一下 X" 可以被理解成 "查一个源" 也可以被理解成 "查到满意为止"。

实测过一次：让它查"上下文压缩方案的局限"，它从 MemGPT 追到 YaRN，从 YaRN 追到 Infini-attention，遇到 429 限流还一遍遍重试，**跑了 28 分钟，核心结论十分钟就拿到了。**

**关键差别：**
- ❌ "查一下 XX 的局限" ← 输入无限
- ✅ "读这三个 URL，摘段落" ← 输入有限，读完就完

---

## 四、多步骤类（容易做到一半忘了在哪）

```
分三步，每步做完都说一句进度：
1. 备份 config.json 到 config.json.bak
2. 把里面的 timeout 从 30 改成 60
3. 跑一次，确认还能启动

哪一步失败就停在那步，告诉我卡在哪。
```

**为什么要求报进度：**
步数多了它会一路冲到底，中间哪步错了都不知道。要求它报，你才看得见。

---

## 五、需要判断的（留白，给规则）

```
看看 D:\Project\某项目 的依赖有没有明显过时的。
不用列全部，挑你觉得最该升级的三个，说为什么。
如果看不出哪些该升，就说看不出来，别硬凑。
```

**为什么留白：**
这种活你要的是它的判断，不是一张清单。**但必须给一个「可以说不」的出口** —— 不然它会为了交差硬凑三个。

---

## 通用原则

**一、先说清「怎么算做完」。**

写代码跑通了就是通了；查资料要写明"只读这几个源"。

**说不出"它怎么知道做完了"，这个任务派下去就是无底洞。**

**二、能验证的，要求它自己验证。**

"写完读回来"、"跑一遍测试"、"确认文件存在" —— 这些比它说"做好了"可靠得多。

**三、你不确定的地方，让它说不确定。**

调查类任务加一句"看不出来就说看不出来"，能省掉很多瞎编。

**四、它会自己加戏。**

不是坏事 —— 说明它在思考。但调查类任务里这个会失控，所以要么限定输入，要么明确说"到此为止"。

---

## 关于权限：写任务前先想一下它要碰哪儿

任务端**默认只有工作区权限**——只能动它自己那个任务目录。

所以：

```
读写的文件在任务目录里        → 直接派，不用管
要动外面的地方（比如 D:\项目\xxx）→ 先给这个窗口提权
```

**怎么提权：** 跟她说「把某某窗口开到完全权限」，或者去桌面端的「环境」页改。

**还有一条：工作区权限下不跑任意解释器。**

```
❌ python -c "..."
❌ node -e "..."
❌ powershell -enc ...
```

**不是因为它们危险，是因为它们能做任何事。**

真要执行代码：**写成文件、放进任务目录、再运行它。**

```
✅ 写个 script.py，然后 python script.py
```

这不是刁难，是让每一步都看得见。

---

## 附：桥会自动加的三条

不管任务内容是什么，`bridge.py` 都会在后面附上：

```
一、能回答了就交。
二、拿不到就记下来、停，别死磕。
三、别扩大范围。
```

这三条是判断标准，不是步骤。**所以上面的写法你该怎么写还怎么写，不用重复它们。**
